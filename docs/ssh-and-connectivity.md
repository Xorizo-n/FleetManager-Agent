# SSH и связь с сервером

Fleet Manager управляет ПК через Ansible по SSH, а агент отвечает за то, чтобы канал оставался рабочим. Здесь описано, как устроены SSH на ПК, самолечение службы, маршруты мимо VPN и обновление без SSH. Протокол обмена с сервером — в [server-protocol.md](server-protocol.md), параметры установщика — в [../installer/USAGE.md](../installer/USAGE.md).

## Как сервер попадает на ПК

1. При регистрации сервер выпускает пару ключей; приватный остаётся в его зашифрованном хранилище, публичный приходит в ответе `register`.
2. Служба кладёт публичный ключ в `C:\ProgramData\ssh\administrators_authorized_keys` и ограничивает права файла SYSTEM и Администраторами (`icacls`). Установка повторяется при каждой синхронизации; ошибки `icacls` не глотаются — иначе Ansible начал бы использовать ключ, который Windows не принял.
3. OpenSSH на Windows принимает этот файл для любого члена локальной группы «Администраторы», поэтому тем же ключом сервер входит и под доменной учёткой (`SshLogin`, например `AT\имя`).
4. Оболочка SSH по умолчанию — Windows PowerShell (сервер работает с `ansible_shell_type=powershell`); под `cmd.exe` любая команда падает.

## Политика порта 22

sshd слушает **22** и отвечает только серверу Fleet Manager:

- правило брандмауэра `FleetManager-Agent-SSH` разрешает TCP 22 только с адреса сервера;
- все остальные разрешающие входящие правила для порта 22 и `sshd.exe` (например, `OpenSSH-Server-In-TCP`, открытое всем) отключаются: Windows пропускает соединение, если подходит хотя бы одно разрешающее правило, и оставшееся открытое правило обнуляло бы ограничение;
- в `sshd_config` добавляется блок между строками `# BEGIN FleetManager SSH source restriction` и `# END FleetManager SSH source restriction`: `Match Address *,!<адрес сервера>` с `DenyUsers *`. Он действует даже там, где групповая политика отменяет локальные правила брандмауэра;
- sshd с портом 5022 (ранние сборки установщика) возвращается на 22.

Адрес источника: `/SshSourceAddress` (IPv4/CIDR через запятую) → значение в `agent.json` → адрес(а) хоста из `ServerUrl`. Если определить адрес не удалось, установщик ничего не трогает: лучше ПК без управления, чем SSH, открытый всем.

## OpenSSH Server

Установщик ставит компонент Windows `OpenSSH.Server` (`Add-WindowsCapability`). Если источник Features on Demand недоступен (WSUS, код `0x800f0954` на SU5-H205-W12/W14; компонент не скачивался на SU5-K306-OP, SU5-K310-OP, SU5-F303-W01), он ставит вшитый MSI Win32-OpenSSH (`{app}\openssh\OpenSSH-Win64.msi`). MSI закреплён по URL и SHA-256 и проверяется на подпись Microsoft в `build-installer.ps1`; в git не хранится, кэшируется в `publish\openssh\`. На ПК, где sshd уже стоит MSI-сборкой (старый `install.ps1`), второй sshd возможностью Windows не регистрируется.

Если sshd поставить не удалось, служба пересылает ошибку из `logs\install.log` в поле `install_error` отчёта `ssh`, а сервер предлагает ремонтную переустановку (`agent_update.repair`) — повторную попытку делает уже установщик.

## Самолечение службы

Каждая синхронизация (по умолчанию раз в 5 минут) выполняет `SshService.Ensure` и `SshHealthChecker.CheckAsync`. Всё, что изменено, попадает в `ssh.repaired`. Если в `agent.json` `KeepSshRunning: false`, агент только сообщает состояние и ничего не чинит.

### sshd (`Core/SshService.cs`)

| Состояние | Действие |
|---|---|
| Запуск вручную (`manual`) | `sc.exe config sshd start= auto` (`start_type`) |
| Остановлен | `sc.exe start sshd` (`started`) |
| Порт слушает, но баннер `SSH-` на `127.0.0.1:22` не приходит («timed out during banner exchange», SU5-F306-W01) | перезапуск после двух пропущенных баннеров подряд (`restarted`); проба идёт там, где sshd реально слушает |
| Отключён (`disabled`) | не трогается — это решение администратора или групповой политики; только сообщается |
| Не установлен | сообщается; `install_error` из `install.log`; сервер предлагает ремонт |

Причина: накопительное обновление Windows (KB5129195, октябрь 2026), обслуживая встроенный OpenSSH.Server, останавливало sshd и молча переводило его на ручной запуск — ПК присылал heartbeat, но выпадал из Ansible.

### Окружение sshd (`Core/SshHealth.cs`)

| Проверка | Если не так | Чинит ли агент |
|---|---|---|
| Правило `FleetManager-Agent-SSH` | нет, выключено, не тот порт/профиль/источник (`firewall_rule`: `missing`/`disabled`/`mismatch`) | да, как в установщике; источник — `SshSourceAddress`, иначе хост `ServerUrl` |
| Блокирующие правила для порта 22 | `firewall_blocking[]` | нет, сообщает |
| GPO, игнорирующая локальные правила | `firewall_ignored_on[]` (профили) и `firewall_gpo_allows` | нет — чинить нужно в GPO; профили сети — `network_profiles[]` |
| `sshd -t` и `Port` в `sshd_config` | `config_valid`, `config_port` | нет, сообщает |
| Блок «только адрес сервера» в `sshd_config` | `source_restricted: false` | нет; сервер предлагает ремонтную переустановку |
| Машинный PATH без `System32` | `path_ok: false` | да (`Core/MachinePath.cs`): иначе Ansible не находит `chcp`/PowerShell (MultiClet SDK обнулил PATH на SU7-M301-W01) |
| `DefaultShell` не PowerShell | `default_shell_ok: false` | да: так оставил MSI, поставленный вручную после агента (SU5-H205-W01…W06) |
| Входит ли SSH-логин в локальные Администраторы (токен S4U с вложенными доменными группами) | `login_is_admin` | нет; раз в час |
| Доверие ПК с доменом (`nltest /sc_verify`) | `domain_trust`: `ok` / `broken` / `unreachable` (нет контроллера: ноутбук дома не считается вышедшим из домена) | нет; раз в час |
| Открытые ключи хоста | `host_keys[]` | — |

Сервер строит из этого список причин в карточке хоста (раздел «SSH», `services/ssh_health.py`), не отдаёт ПК ожидающие задачи, пока SSH заведомо закрыт, и сверяет ключи хоста по идентификатору хоста (`HostKeyAlias`), а не по IP: после подготовки ПК из образа (новые ключи) или смены адреса по DHCP общий `known_hosts` давал «REMOTE HOST IDENTIFICATION HAS CHANGED».

Отчёт старше 20 минут сервер для решений не использует.

## Маршруты мимо VPN

Встроенный клиент Windows на SU5 строит полнотуннельный VPN: интернет идёт через него, а вместе с ним и трафик к серверу. Heartbeat приходил бы с адреса из пула VPN, ответы SSH уходили бы в туннель, и ПК выпадал из Fleet Manager. `ServerRouteKeeper` (`Service/ServerRouteKeeper.cs`, планировщик — `Core/ServerRoute.cs`) держит маршрут `/32` до нужного адреса через шлюз физической карты — он длиннее по префиксу и выигрывает у маршрутов VPN, остальной трафик пользователя не затрагивается.

Правила (общие для трёх видов адресов):

- маршрут **непостоянный** (`route.exe add`, без `-p`): после перезагрузки служба возвращает его сама;
- кандидаты — только включённые физические адаптеры (проводные и Wi-Fi) с IPv4-шлюзом; виртуальные и VPN-адаптеры (по имени: `vpn`, `tap-`, `wireguard`, `hyper-v`, `vmware` и т. д.) и тип `Ppp` пропускаются;
- адрес должен лежать в приватном блоке (10/8, 172.16/12, 192.168/16); подходят адаптеры, чей адрес в том же блоке, а шлюз — в подсети адаптера. Если сервер в подсети самого адаптера, маршрут не нужен. Среди подходящих выбирается проводной, затем с меньшим индексом;
- **доверенные шлюзы**: маршрут ставится только через шлюз, через который сервер уже отвечал без VPN. Шлюз запоминается после успешного heartbeat (`ConfirmPathAsync`), если по `GetBestInterface` ответ шёл физическим адаптером; хранится до 16 штук в `server-route.json`. Поэтому ноутбук в другой сети — даже тоже 10.x — не получает маршрута мимо своего VPN;
- перед сохранением маршрута проверяется TCP-порт: если адрес по новому маршруту не отвечает за 3 секунды, маршрут сразу удаляется; неудачный план не повторяется 10 минут (только на следующих синхронизациях);
- переопределение сети (подключение или отключение VPN) обрабатывается через `NetworkChange.NetworkAddressChanged` с паузой 5 секунд;
- `PinServerRoute: false` в `agent.json` — не трогать маршруты вообще.

Что закрепляется:

| Адрес | Источник | Проверка порта | Зачем |
|---|---|---|---|
| Сервер Fleet Manager | `ServerUrl` | порт из URL | heartbeat и SSH-ответы |
| Точка раздачи | `pin_routes` из ответа на heartbeat, запоминается в `server-route.json`; нет поля — маршруты снимаются | порт из `pin_routes` | nginx на точке раздачи отвечал 403 на адрес из пула VPN, и установщик с файлами плейбуков шёл через сервер (~30 Мбит/с против ~900 по HTTP; SU5-J108-W02/W04/W05/W08) |
| Контроллеры домена (`Core/DomainControllers.cs`) | DNS-серверы физических адаптеров (до 6 адресов, без loopback и link-local) плюс контроллер из `DsGetDcName` | LDAP, TCP 389 | без контроллера вход доменной учётки по SSH обрывается после обмена ключами, и агент пишет `domain_trust: unreachable` (SU5-J108-W02, ПК с VPN `UrFU`) |

## Обновление без SSH

Если до ПК нельзя достучаться по SSH, а обновить агента надо (чтобы доставить исправление, возвращающее SSH), сервер передаёт предложение в ответе на heartbeat, а агент скачивает и ставит версию сам. Механика, условия и ограничения — в разделе «Самообновление» [server-protocol.md](server-protocol.md#самообновление).

## Запасной вход под локальным администратором (в разработке на сервере)

Доменная учётка не пускает по SSH, когда нарушено доверие с доменом (SU5-I203-W03), недоступен контроллер (SU5-J108-W02 с VPN) или учётка отключена. Серверная ветка `feature/local-admin-fallback` (на 2026-10-29 не слита и не развёрнута) учит сервер входить в таких случаях под локальным администратором тем же ключом (`services/local_admin.py`). Локальная учётка создаётся при вводе ПК в домен ([AutoDomain](https://github.com/Xorizo-n/AutoDomain)), а её пароль ставит плейбук `set_local_admin_password.yml`. Признак «есть ли такая учётка и в администраторах ли она» (`ssh.local_admin`) сервер ждёт от агента, но агент его пока не присылает — это работа для агента, когда серверная часть будет готова. См. также [server-protocol.md](server-protocol.md#совместимость-версий).
